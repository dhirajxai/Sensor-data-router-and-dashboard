## Overview
This project is a full-stack vehicle telemetry visualization system built with React. These instructions ensure consistent, high-quality code that prioritizes real-time performance, modularity, and developer experience.

---

## Senior Engineering Principles

### 1. **Maintainability First**
- Write code that is easy to understand at a glance.
- Use clear naming conventions: functions describe actions (`fetchVehicleLocation`), variables describe state (`isLoading`), components are PascalCase (`VehicleMap`).
- Avoid clever one-liners that sacrifice clarity. A 3-line readable solution beats a 1-line cryptic one.
- Keep functions and components focused on a single responsibility.

### 2. **Complete Implementations**
- When writing code, implement fully rather than leaving TODOs or stubs.
- Include error handling, edge cases, and type safety.
- If a component needs loading states, provide them. If data can fail, handle it gracefully.
- Do not create half-implemented features; finish or clearly document what remains.

### 3. **Consistency Across Services**
- **Frontend & Backend**: Use the same naming conventions for data structures (e.g., `vehicleId`, not `id` in one place and `vehicle_id` elsewhere).
- **API Design**: All telemetry endpoints follow RESTful patterns with consistent response structures.
- **Error Responses**: All errors include `code`, `message`, and optional `details` fields.
- **Data Types**: Define shared TypeScript interfaces in a common `types/` directory.

### 4. **Ask Clarifying Questions**
- If a requirement is ambiguous, ask before implementing.
- Document assumptions you make while waiting for clarification.
- Suggest sensible defaults when appropriate.

### 5. **Infer Sensible Defaults**
- For React components, assume responsive mobile-first design unless specified.
- For real-time data, assume WebSocket for high-frequency updates, REST polling for low-frequency.
- For error messages, default to user-friendly language, not technical jargon.
- Performance defaults: debounce rapid updates (500ms), cache vehicle metadata (5 min), lazy-load map tiles.

### 6. **Continue Unfinished Implementations**
- If code is incomplete, automatically complete it based on project patterns.
- Do not ask if you should finish—just do it.
- Maintain consistency with existing code style and structure.

### Custom Hooks
- Keep hooks focused: one responsibility per hook.
- Export hooks from `/hooks/index.ts` for consistent importing.
- Name hooks descriptively: `useVehicleLocation`, `useTelemetryUpdates`, `useCacheVehicles`.
- Always include cleanup in useEffect (unsubscribe, abort requests).

### State Management
- Use React Context for shared global state (auth, active vehicle, theme).
- Use local useState for component-specific state.
- For complex state, use useReducer or a library (Redux, Zustand) only if multiple components depend on it.

### Real-Time Data Handling
- Use WebSockets for continuous telemetry streams.
- Implement debouncing for high-frequency updates (e.g., GPS every 100ms → UI update every 500ms).
- Gracefully degrade to polling if WebSocket is unavailable.
- Always show last-known data while connecting/reconnecting.

## Backend Guidelines (Node.js/Express)

### API Response Format
All endpoints return consistent JSON structure:
```typescript
interface ApiResponse<T> {
  success: boolean;
  data?: T;
  error?: {
    code: string;        // e.g., "VEHICLE_NOT_FOUND"
    message: string;     // User-friendly message
    details?: unknown;   // Optional technical details
  };
  timestamp: string;     // ISO 8601
}
```

### Telemetry Data Structure
```typescript
interface TelemetrySnapshot {
  vehicleId: string;
  timestamp: string;     // ISO 8601
  location: {
    latitude: number;
    longitude: number;
    accuracy?: number;   // meters
  };
  metrics: {
    speed: number;       // km/h
    heading?: number;    // degrees (0-360)
    temperature?: number;// Celsius
    batteryLevel?: number; // percentage (0-100)
    [key: string]: number | undefined; // extensible
  };
}
```

### Controllers & Services Separation
- **Routes**: Define endpoints, validate input, handle HTTP concerns.
- **Controllers**: Orchestrate business logic, call services.
- **Services**: Pure business logic, external integrations, database queries.

```typescript

  }
```

### Error Handling
- Use centralized error middleware.
- Always catch async errors (`express-async-errors` or wrap in try-catch).
- Return appropriate HTTP status codes (400 bad request, 404 not found, 500 server error).
- Log errors with context (user ID, vehicle ID, timestamp).

### WebSocket Implementation
- Use Socket.IO or ws library for real-time telemetry streams.
- Implement namespaces: `/telemetry`, `/alerts`, `/commands`.
- Authenticate socket connections.
- Implement reconnection logic with exponential backoff on client side.

## Performance Optimization

### Frontend
1. **Code Splitting**: Use React.lazy for route-based components.
2. **Memoization**: Use `React.memo`, `useMemo`, `useCallback` for expensive computations.
3. **Virtual Scrolling**: For long lists of vehicles, use react-window.
4. **Debounce/Throttle**: Debounce search inputs, throttle scroll events.
5. **Asset Optimization**: Lazy-load map tiles, compress images.

### Backend
1. **Caching**: Cache vehicle metadata (Redis), telemetry snapshots (5-min TTL).
2. **Database Indexing**: Index `vehicleId`, `timestamp` for telemetry queries.
3. **Pagination**: Always paginate telemetry history (default: 100 items per page).
4. **Connection Pooling**: Use connection pools for databases and external APIs.

### Real-Time Data
- Batch telemetry updates: send 10 updates per second max to frontend.
- Compress payloads: send only changed fields, not entire snapshots.
- Use binary protocols (e.g., Protocol Buffers) for high-throughput scenarios.

## Testing & Quality

### Frontend Testing
- **Unit Tests**: Test components, hooks, utilities in isolation.
- **Integration Tests**: Test component interactions and data flows.
- **E2E Tests**: Test critical user journeys (view vehicle, monitor telemetry).
- Tools: Vitest, React Testing Library.

### Backend Testing
- **Unit Tests**: Test controllers, services, utilities.
- **Integration Tests**: Test API endpoints with database.
- **Test Database**: Use separate test database, reset before each test.
- Tools: Jest, Supertest.

### Code Quality
- **Linting**: ESLint for JavaScript/TypeScript (no console.log in production).
- **Type Checking**: Enable strict mode in TypeScript.
- **Formatting**: Prettier for consistent code style.
- **Pre-commit Hooks**: Use Husky to run linters before commits.

## Coding Conventions

### Naming
- **Files**: kebab-case for components (`vehicle-map.tsx`), snake_case for utilities (`fetch_api.ts`).
- **Functions/Variables**: camelCase.
- **Constants**: UPPER_SNAKE_CASE.
- **Types/Interfaces**: PascalCase, prefix with `I` only if absolutely necessary (avoid `IVehicle`, use `Vehicle`).

### Comments
- Write self-documenting code; comments explain "why", not "what".
- Use JSDoc for public functions and exported components.

### Git Conventions
- Branch naming: `feature/vehicle-tracking`, `fix/map-zoom`, `chore/dependencies`.
- Commit messages: `feat: add real-time vehicle tracking`, `fix: resolve map rendering lag`.

## Decision-Making Framework

When faced with ambiguity:
1. **Performance?** → Optimize for the most critical path (real-time updates).
2. **Simplicity vs. Flexibility?** → Start simple, refactor to be flexible only when needed.
3. **Framework choice?** → Default to what the team knows; don't introduce unnecessary dependencies.
4. **Error handling?** → Always default to graceful degradation, never silent failures.

## Example Workflow

When assigned a task like "Add real-time speed monitoring":

1. **Clarify**: Are updates streamed via WebSocket or polled? UI refresh rate?
2. **Design**: Sketch component structure, data flow, WebSocket events.
3. **Implement Frontend**: SpeedGauge component, useSpeedUpdates hook, styling.
4. **Implement Backend**: /telemetry/speed endpoint, WebSocket event handler, database schema.
5. **Test**: Unit tests for component and hook, integration test for API.
6. **Document**: Add JSDoc comments, update README if needed.
7. **Review & Optimize**: Check performance, cache strategies, error handling.
